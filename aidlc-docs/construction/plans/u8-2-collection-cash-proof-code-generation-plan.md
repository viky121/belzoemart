# Code Generation Plan: U8.2 Collection, Cash and Proof
This plan is the single source of truth for U8.2 code generation. Tick each step the moment it is done.
Workspace root: `/home/viky/Belzo` (brownfield monorepo: `apps/api`, `apps/web`, `apps/mobile`, `packages/shared`). Application code goes in those folders, never in `aidlc-docs/`. Docs summaries go in `aidlc-docs/construction/u8-2-collection-cash-proof/code/`.
## Unit context
- **Unit**: U8.2 Collection, cash and proof (see `unit-of-work.md`). Requirements: DL-5.x (collection, cash, UPI QR), DL-6.x (proof), DL-7.x (cash book, settlement), COD stock and invoice after delivery. Traceability is by BR-C id (BR-C1 to BR-C56), properties Q1 to Q12, patterns SP10 to SP16 and RP7 to RP12.
- **Design inputs**: `functional-design/` (domain-entities, business-rules, business-logic-model), `nfr-design/` (nfr-design-patterns, logical-components).
- **Depends on**: U8.1 (JobService, gate registry, worker, views, security events) and the existing Razorpay payment provider, storage port, webhook entry, inventory and invoice services.
- **Used by**: U8.3 (admin cash screens), U8.4 (partner PWA), U8.5 (customer side).
- **Database entities owned**: DeliveryCollection, DeliveryQrCode, DeliveryCashEntry, DeliverySettlement, DeliveryProof (migration 2).
- **Not in this unit**: any screen (U8.3, U8.4), customer e-mails (U8.5), earnings, cash limits, part-cash/part-UPI, partner-visible refunds.
- **Rules for generation**: modify existing files in place; no `_new` or `_copy` files; follow existing style (NestJS modules, zod DTOs, Prisma, Jest specs next to source, `@belzo/shared` imports); no new runtime dependency; nothing is deployed until you say "deploy".
- **Constraints carried from the design**: QR calls use their own breaker names `razorpay-qr` and `razorpay-refund`, never `razorpay`; lock order is job first, then partner; the cash book is written only through `LedgerService`; the amount always comes from the job, never from the client.
