# Customer order-detail redesign: live status, cancel and return flows

Commits fa79073..2b7d7c1 on master rebuild the customer order page around the order status. A shared `reconcileTracking` makes stale shipments and events (the "packed" vs "delivered" bug) agree with the order when it is read. The mock courier now follows the order, and `syncTracking` dedupes events and walks legal transitions. The return flow gets standard reasons, a dedicated photo-upload endpoint, and server-side checks for photos, own-storage URLs and item quantities. The web page is split into pure helpers (`order-view.ts`, unit-tested) and presentational sections, two accessible modals, and a 30 s poll that runs only while the order can still change. Ownership checks, schema, ORDER_TRANSITIONS, canCustomerCancel, pricing and invoices are untouched. All seven verification commands plus the web build pass on rerun.

Watch for: COD customers are offered "Refund to Belzo wallet", but the backend credits ₹0 for COD and still marks the return Refunded (confirmed). Photo enforcement can be bypassed with free text such as "Damaged" sent without a code (confirmed). Derived "Delivered"/"Cancelled" times come from `order.updatedAt`, which invoice regeneration bumps (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Live status works as specified. The badge and stepper read only `order.status`. `tracking.latestStatus` is the furthest of the order, shipment and event statuses, with terminal order states always winning. Steps the courier never reported are added as `derived` events. Only the derived step for the current status gets a time, and that time is `order.updatedAt`, which is not a true transition time.

The return API now enforces the photo rule, own `returns/<uuid>.<ext>` URLs, that items belong to the order, and that quantity stays within what remains. The photo rule only matches exact codes or exact label prefixes. Resolution rules and the Other-comment rule are enforced only in the browser.

The resolution step is where customer money is promised. `resolutionOptions` always offers wallet refunds. `processReceived` clamps every refund to the captured payment, and COD payments are never captured. The return flow therefore promises a wallet credit that never happens.

The UI meets the checklist: header, stepper, item cards, a price card from `breakupView` with 2-decimal paise, a newest-first timeline, a return card, one primary action, and modals with focus trap, Esc and scroll lock. Two small gaps: in-transit orders get no explanation for the missing Cancel button, and disabled Next/Continue buttons are not linked to the hint that explains why.

<summary>Details</summary>

### COD returns: "Refund to Belzo wallet" credits nothing

`resolutionOptions` (`apps/web/src/lib/order-view.ts`) always offers `refund_wallet`, described as "Credited to your wallet once the item is received". Plan decision 7 drops `refund_source` for COD because it refunds nothing, but `refund_wallet` has the same problem. `ReturnService.processReceived` computes `toRefund = clampRefund(refundAmount, captured?.amount ?? 0)`. COD payments are created with `status: 'pending'` (`checkout.service.ts:298`), and nothing ever marks them captured, since `markCaptured` is webhook-only. So `toRefund` is 0, `wallet.earn` is skipped, and the return is still written as `refunded` (confirmed).

The customer sees a "Refunded" return badge and a "Refunded" stepper step (from `refundStep`) without receiving any money. COD is the default payment for many shoppers here, so this hits the main return path. The backend gap predates this change. This redesign is what puts the promise in front of customers.

The fix involves a business choice, and changing money math is out of scope for this task. One option is to change the COD copy or options so no automatic credit is promised; replacement-only also covers "No longer needed" poorly, since it has no replace option. The other is to get the owner's approval to treat delivered COD orders as paid when clamping wallet refunds.

### Photo rule matches only exact codes and labels

`returnReasonRequiresPhotos` takes the stricter of `findReturnReason(reasonCode)` and `findReturnReason(reason)`. The text lookup matches either an exact, case-sensitive code or a case-insensitive label equal to the text before the first ':'. As a result, `{reason: "Damaged"}`, `{reason: "Damaged/broken product"}` and `{reason: "Wrong item"}` with no `reasonCode` all pass without photos (confirmed by tracing `findReturnReason`).

The storefront always sends the code, so only direct API callers can bypass it. The task asked for enforcement by reason text as well, though.

### Server accepts any resolution for any reason

The controller zod only checks that `resolution` is one of the three values. Replace for "No longer needed", `refund_source` on a COD order, and Other with an empty comment all pass server-side. Only `returnStepError` in the browser blocks them (confirmed). The shared `RETURN_REASONS` already holds `allowReplace` and `commentRequired`, so mirroring the rules in `ReturnService.request` takes only a few lines.

### Derived milestone times come from order.updatedAt

`reconcileTracking` stamps the derived event for the current status with `order.updatedAt` when it is newer than the last real event. `buildStepper` uses `updatedAt` for the Cancelled and Returned steps. `Order.updatedAt` is bumped by any order write. `InvoiceService.generate` (line 71) and `regenerate` (line 90) both write `order.invoiceUrl`. After an admin regenerates an invoice, a delivered order's "Delivered" time becomes the regeneration time (confirmed by the code path).

The value is a real timestamp, but of a different event. There is no status history, so the honest choice for derived steps is `occurredAt: null`, which the UI already renders as "Time not available".

### Action card and modal accessibility

For packed, shipped and out-for-delivery orders, the Actions card shows Reorder, Invoice and Need help, with no explanation for why Cancel is missing. The page explains ineligibility only for returns on delivered or returned orders (confirmed in `page.tsx`).

In both modals the blocking reason is a plain `<p class="od-modal__hint">`, and it is not linked to the disabled Next, Submit or Continue buttons. A screen-reader user reaches a disabled button with no stated reason (likely).

### Test coverage

Every spec listed in the plan exists and passes. Not tested: duplicate `orderItemId` rejection, non-returnable item rejection, free-text defect reasons sent without a code, and server-side resolution rules (none exist yet).
